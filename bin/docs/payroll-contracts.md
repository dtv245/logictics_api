# Multi-jurisdiction payroll contracts

015G: privileged payroll roles can list open reconciliation cases and submit `POST /api/payroll/payments/{id}/reconcile-bank`. The authenticated actor must resolve to a persisted employee. Each append-only BANK/APPLIED event records case, source, unique bank transaction, exact amount/currency, destination counterparty, evidence reference, reason, occurrence time and actor. Run/payment/case locks serialize retry and case resolution; the idempotency key replays only identical structured inputs by the same actor. One bank transaction can be claimed once. Late confirmed success may move a failed payment/item to success/PAID only through an explicit matching open case; it does not unlock or mutate payroll inputs. Existing success cannot be downgraded. V19 is forward-only and supplies transaction uniqueness, insertion evidence checks, success guards and the narrow failed-item-to-paid trigger exception. No provider evidence is fabricated and no transfer is initiated by reconciliation.

Payroll completion domain decision: `PayrollPayment` is the actual money transaction (`SUCCEEDED` on confirmed transfer); `PayrollRunItem` has payment outcome `PAID` or audited `NO_PAYMENT_REQUIRED`; `PayrollRun` is a processing batch and becomes terminal `COMPLETED` iff every item is `PAID` or `NO_PAYMENT_REQUIRED`. A run is never named `PAID`. The no-payment command is `POST /api/payroll/items/{id}/no-payment-required`, requires a locked run, an unattempted `CALCULATED` or `SCHEDULED` item with exactly zero net, persisted actor, supported reason code (`ZERO_NET_PAY`, `FULLY_OFFSET_BY_DEDUCTIONS`, `MANUAL_ADJUSTMENT_ZERO_BALANCE`) and nonblank explanation, with no payment attempt or unresolved case. It creates no fake zero-value payment. It stores `noPaymentRequiredAt`, `noPaymentRequiredBy`, reason code/text; same actor and same reason replay idempotently, differing input conflicts. A zero-net settlement remains `LOCKED` as immutable calculation history; payment status comes from the payroll item/payment. Completion captures timestamp, optional actor and source (`PAYMENT_PROVIDER`, `BANK_RECONCILIATION`, or `NO_PAYMENT_DISPOSITION`). Run and item database triggers enforce terminal-state, audit and immutability rules. V20 migrates historical run `PAID` to `COMPLETED` with source `LEGACY_PAID_RUN`, retaining the old `paid_at` database column as unmapped historical data.

Invoice Task 5.4: entity and API request payroll-era fields are deprecated. Invoice create/update rejects any supplied legacy employee/period/distance input with `INVOICE_LEGACY_PAYROLL_FIELD`; the employee search filter is rejected explicitly. MapStruct ignores legacy payroll columns during create/update. Historical response fields remain deprecated, read-only compatibility projection; no new invoice command writes them. Database columns/history are retained (no destructive migration).

Architecture: MULTI_JURISDICTION. Tax implementations are pluggable by explicit policy calculator key. The current implementation is a jurisdiction-neutral framework; region-specific policies/adapters are added incrementally from authoritative inputs. Production has no statutory tax adapter or guessed legal rate. Test-only fixed numbers prove arithmetic and are not regional tax rules.

Jurisdiction contains ISO alpha-2 country, optional subdivision and optional locality. A locality does not require a subdivision. WorkerClassification is an independent EMPLOYEE/CONTRACTOR profile dimension; neither implies zero tax. Resolution is work/payroll override → latest effective employee profile → tenant default. Each tenant's existing database owns its settings singleton. Missing jurisdiction/profile/policy/adapter returns a named UNAVAILABLE reason and VALIDATION_REQUIRED. Taxes/net stay null; gross/deductions/reimbursements remain explainable.

Policy resolution uses the exact resolved jurisdiction and worker classification at the explicitly supplied effectiveDate. Core does not infer that a country-only policy applies to every locality. An adapter/policy may explicitly compose national/regional/local rules. Latest started versions supersede earlier versions in the same code family; inactive/expired newer versions cannot resurrect older open-ended rows. Multiple eligible policy families are ambiguous. Configuration requires an explicit calculator key and authoritative-source reference; source verification and legal implementations are future regional adapter work.

Profiles/policies/jurisdiction identities are append-only and database-protected. Profile versions preserve employee identity; policy versions preserve code/jurisdiction/classification and use increasing effective dates. Tax snapshots include jurisdiction resolution/profile identity, worker classification, policy ID/version/full inputs, explicit effectiveDate, source line IDs/categories/economic signs/taxable evidence, additional tax inputs, adapter key/version/inputs/outputs, availability/reason and rounding identity. Recalculation is explicit before review/lock and appends immutable calculation_snapshots, preserving earlier unavailable explanations.

Only locked settlements in the explicit payroll period and same currency can be mapped. Settlement rows are locked in UUID order and one global settlement→item claim prevents duplicate payroll. Request-key retry verifies original structured inputs; drift rejects. Gross follows economic source line classification. Reversal traces parent line IDs recursively and reverses the original economic sign; its payment line class must not inflate gross or taxable earnings. Components reconcile to each settlement net. Standalone negative recovery requires an explicit recovery policy/workflow and retains signed amounts with null payable net; no clamping to zero or negative payment.

Supplement deductions/reimbursements require explicit unique source IDs, descriptions and positive currency-rounded amounts. Their immutable persisted source claims prevent reuse. Voluntary/expense components are separate from statutory tax/insurance withholding. Adapters receive detailed source evidence and define statutory bases; core does not infer taxable treatment from contractor status, invoice tax or customer amount. The existing V11 income_tax_amount/insurance_amount represent employee payroll withholding; any employer-side costs must be explained in adapter outputs and a separate future projection.

Available payable net = gross − other deductions − income tax − insurance + reimbursements. Reconciliation uses configured financial rounding. Tax availability requires nonnegative resolved amounts and a versioned policy. Database and application gates reject APPROVED/LOCKED/PAYMENT_SCHEDULED while required statutory inputs are unavailable. LOCKED does not imply PAID; payment orchestration is a subsequent sub-task.

V11 remains immutable. V14 adds forward configuration, snapshots, availability, supplement source claims and signed reversal components. Existing tax columns are not backfilled with zeros. 015D: workflow lock issues immutable payslips/PDF inside the same transaction. Artifact-generation failure rolls back lock; retry returns the original ID/audit/PDF. V16 stores bytea PDF, SHA-256, renderer version and issuance actor, leaving historical V11 external-document references untouched. Payslip captures employee name at issuance and immutable financial/tax/source inputs; future employee/profile changes cannot change the issued artifact. Unicode DejaVuSans is bundled with its license; a configurable font resource must cover additional scripts, otherwise issuance returns PAYSLIP_FONT_UNSUPPORTED. Monetary display uses currency scale without further rounding/scientific notation. Driver list/detail/PDF routes enforce ownership; administrative payroll roles can inspect within their tenant. No external messages or transfers are issued. PDF content is private/no-store. Historical PDFs missing a persisted artifact return explicit availability errors. PDFBox 3.0.8 dependency verified from https://pdfbox.apache.org/3.0/getting-started.html. Clean/upgraded regression: 169 tests, 0 failures/errors, 1 legacy skip; 32 PG cases.

015E: scheduling requires resolved locked payroll, issued payslip, persisted actor and unique request key. Amount/currency come from immutable item net; caller cannot supply a payout total. STRIPE destination must match the actual employee connected-account field; bank/provider destination references are explicit. Payment attempts snapshot identity/policy/amount/destination and retain original history. One active attempt per item; new key/input drift rejects. Parent run ID is read as a scalar before parent/item/payment locks to prevent stale-context races. Dispatch commits PROCESSING intent before provider I/O; accepted submission remains PROCESSING awaiting verified completion. No production provider adapter exists; missing adapter stays SCHEDULED. Unknown outcome stays PROCESSING and retries do not create another external request/attempt; reconcile verified evidence. Zero-net items require an explicit no-payment disposition policy. Test-only provider is local and sends no real transfer. V17 clean/upgraded regression: 174 tests, 0 failures/errors, 1 legacy skip; 34 PG cases.

015F: provider callback is public only through a configured authentication verifier. Production has no verifier/adapter, so callbacks fail closed; test signature is fixture-only. Verifier returns authenticated event identity and, with tenancy enabled, a trusted tenant resolved from provider/merchant registry. Unsigned headers/body never choose a tenant. Existing tenant registry validates active tenant before database transaction; conflicting JWT tenant rejects and thread context is restored. Original verified body/proof is preserved alongside canonical event inputs. Event ID retry checks structured financial identity, not transport whitespace or proof timestamps.

V18 journal/evidence guard requires exact payment/currency/amount/reference. Verified success updates only its item and mapped settlements; the run becomes `COMPLETED` only after all items are terminal (`PAID` or `NO_PAYMENT_REQUIRED`). Customer invoice fields and shipment-cost projection are untouched. Verified failure retains attempt history, leaves sources scheduled/unpaid and permits a fresh attempt. Late/conflicting outcomes create immutable reconciliation cases and block dispatch/new attempts; no automatic downgrade/retry or duplicate payout. Database rejects payment/item/settlement paid flags without matching successful evidence. Clean/upgraded regression: 184 tests, 0 failures/errors, 1 legacy skip; 38 PG cases (pre-V20 baseline).
